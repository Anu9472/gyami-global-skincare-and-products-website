# Production deployment

## Render backend

The repository-root `render.yaml` provisions the NestJS API, PostgreSQL,
database migrations, the idempotent production seed, and a health check.
The supplied blueprint uses Render's free plans only as a demonstration
starting point; it is not an enterprise production configuration. Upgrade the
web service and database to managed plans with a documented backup/restore
policy before launch.

Private KYC, complaint, and return-evidence documents plus review photos are
stored through the S3-compatible object-storage adapter. Production configuration refuses
to start without the required bucket and region, preventing accidental use of an
ephemeral web-service filesystem for regulated documents.

During initial Blueprint creation, provide:

- `CORS_ORIGINS`: the single public marketplace origin
- `CUSTOMER_WEB_URL`: the single public marketplace origin
- `VENDOR_WEB_URL`: optional Vendor Panel origin used in password-reset links;
  defaults to `<CUSTOMER_WEB_URL>/vendor` in production
- `THROTTLE_REDIS_URL`: managed Redis or Valkey `redis://`/`rediss://` URL for
  distributed API rate limiting
- `TRUST_PROXY_HOPS=1`: Render's single trusted reverse-proxy hop, so
  rate-limiting and access logs use the client address rather than the load
  balancer address. Do not increase this value unless the network path is
  documented and controlled.
- `ADMIN_EMAIL`: initial production administrator email
- `ADMIN_PASSWORD`: strong unique password (minimum 12 characters)
- `DOCUMENT_STORAGE_S3_BUCKET`: private, non-public bucket for KYC, support, and review files
- `DOCUMENT_STORAGE_S3_REGION`: bucket region (or provider-specific value, such as `auto`)
- `DOCUMENT_STORAGE_S3_ACCESS_KEY_ID` and `DOCUMENT_STORAGE_S3_SECRET_ACCESS_KEY`:
  minimum-privilege credentials limited to that bucket, unless workload identity
  is used instead. Grant object read/write access plus `s3:ListBucket` (or the
  equivalent bucket-head permission) so the readiness endpoint can verify the
  configured bucket without uploading a probe file.
- `DOCUMENT_STORAGE_S3_ENDPOINT`: required for an S3-compatible provider such
  as Cloudflare R2 or MinIO; leave blank for AWS S3
- `DOCUMENT_STORAGE_S3_FORCE_PATH_STYLE=true`: only when required by the
  selected S3-compatible provider
- `DOCUMENT_STORAGE_S3_SERVER_SIDE_ENCRYPTION=AES256`: explicitly requests
  encryption at rest for every private object. Use `aws:kms` or
  `aws:kms:dsse` with `DOCUMENT_STORAGE_S3_KMS_KEY_ID` when a customer-managed
  KMS key and its rotation/audit controls are required. The selected
  S3-compatible provider must support the standard S3 server-side-encryption
  request headers.
- `SMS_PROVIDER`: set to `MSG91` (the production default)
- `MSG91_WIDGET_ID`: the OTP Widget ID shown in MSG91 Client Side Integration
- `MSG91_WIDGET_TOKEN`: the widget-scoped client token selected in MSG91
- `MSG91_AUTH_KEY`: server-only key used by `/api/v5/widget/verifyAccessToken`

Customer authentication uses MSG91's default OTP Widget SMS configuration. The
Widget ID and client token initialize the browser challenge; the server-only
auth key verifies the returned access token and binds it to the expected mobile
number. A custom sender ID, DLT entity ID, or custom OTP template is not
required for this mode.

JWT and encryption keys are generated by Render. At first startup, the
blueprint creates the configured `ADMIN_EMAIL` only if it does not yet exist;
it never resets an existing administrator password. If that email already
belongs to a non-admin account, startup stops rather than silently escalating
the account. Provider credentials are added after the first deployment through
Admin Panel -> System configuration and are encrypted in PostgreSQL.

`MSG91_OTP_TEMPLATE_ID` is retained only for the separate legacy
server-generated OTP provider and is not used by customer authentication. The
server auth key is never sent to the browser; it is masked in the Admin API and
encrypted at rest.

## Vercel frontends

Create three Vercel projects from the same Git repository with these Root
Directories. The customer project is the public gateway; the admin and vendor
projects are implementation origins reached through its rewrites.

| Project | Root Directory | Production environment variables |
| --- | --- | --- |
| Customer / public gateway | `apps/customer-web` | `VITE_API_MODE=http`, `VITE_API_URL=https://<render-host>/api/v1` |
| Vendor | `apps/vendor-panel` | `VITE_API_BASE_URL=https://<render-host>/api/v1` |
| Admin | `apps/admin-panel` | `VITE_API_BASE_URL=https://<render-host>/api/v1` |

All three frontend bundles fail fast in production if these API settings are
missing. This deliberately prevents customer mock data or an unintended relative
API endpoint from being used on a live domain.

The customer Content Security Policy deliberately permits only the Razorpay
checkout script and checkout/API frames needed for prepaid checkout, the MSG91
OTP-widget loader origins, and the optional Google Identity origins. Do not
remove `checkout.razorpay.com`, `api.razorpay.com`, `verify.msg91.com`, or
`verify.phone91.com` from that policy without replacing the associated
integration and verifying a prepaid payment and mobile OTP flow.

Public routing is:

- `/` and customer routes -> customer bundle
- `/admin` and `/admin/*` -> existing admin bundle
- `/vendor` and `/vendor/*` -> existing vendor bundle
- `/api/*` -> Render API

The admin and vendor production builds use `/admin/` and `/vendor/` asset and
React Router bases. Their Vercel projects rewrite those deep links to the
corresponding SPA entry point. The public gateway routes the prefixes before
its customer SPA fallback, so it must remain the only user-facing domain.

## Post-deployment checks

After the service is exposed through its production HTTPS domain, run the
non-mutating verifier from a secure operator shell:

```sh
VISHWANEED_PRODUCTION_API_URL=https://api.example.com/api/v1 \
METRICS_AUTH_TOKEN='<secret held by the monitoring service>' \
npm run verify:production-readiness
```

It validates API readiness, launch readiness, and protected process metrics.
Do not add the token to a URL or the repository.

1. API readiness at `/api/v1/health/ready` (database, private document storage,
   and the configured distributed rate-limit store), liveness at `/api/v1/health/live`,
   and production launch readiness at `/api/v1/health/launch`. The launch gate
   additionally requires Razorpay, Shiprocket, MSG91, and Interakt settings.
   Swagger is intentionally disabled
   by default in production and should only be enabled for controlled support work.
2. Customer, vendor, and administrator authentication and refresh tokens.
3. Public categories/products and authenticated cart operations.
4. Vendor ownership and administrator RBAC.
5. Razorpay order creation and signed webhook verification in test mode.
6. Shiprocket authentication/rate lookup and signed webhook verification.
7. Interakt approved-template delivery to an opted-in test number.
8. Customer registration and password-reset verification through the MSG91
   Widget, including a successful browser challenge and server-side access-token
   verification for an opted-in test number. Do not accept a simulated delivery
   in production.
9. Authorized private document upload and download. Confirm the created object
   is private, encrypted, retained according to policy, and still available
   after a redeploy.

Do not perform a real payment, shipment purchase, or production WhatsApp send as
part of an automated smoke test.
